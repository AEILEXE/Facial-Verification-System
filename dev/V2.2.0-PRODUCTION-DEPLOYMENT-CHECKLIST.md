# FANS-C v2.2.0 — Production Deployment Checklist

Scope: putting `FANS-C-Setup-v2.2.0.exe` onto a real barangay server for the
first time (fresh hardware/OS, no prior FANS-C install). For an existing
FANS-C install being updated to v2.2.0, use
`V2.2.0-UPGRADE-CHECKLIST.md` instead — do not run this checklist against a
machine with production beneficiary data already on it.

This checklist assumes `docs/DEPLOYMENT-CHECKLIST.md` (the general,
version-independent deployment checklist) is followed in full; only the
items specific to what changed in v2.2.0 are repeated here for convenience.

---

## 1. Before installing

- [ ] Confirm this is genuinely a fresh machine — no `db.sqlite3`, no
      `.env`, no `backups/` directory with real data. If any of these
      exist, stop and use the upgrade checklist instead.
- [ ] Server meets the baseline requirements in
      `docs/DEPLOYMENT-CHECKLIST.md` (Windows version, network, firewall
      ports 443/8000).
- [ ] Installer SHA-256 matches the value recorded in
      `V2.2.0-RELEASE-INSTALLATION-CHECKLIST.md`'s sign-off table — confirms
      the file wasn't corrupted or substituted in transit.

## 2. Install

- [ ] Run `FANS-C-Setup-v2.2.0.exe` as Administrator.
- [ ] **Fresh-install dialog** appears (not the upgrade dialog) — confirms
      the installer correctly detected no prior version.
- [ ] Installer completes with no errors; Task Scheduler tasks "FANS-C
      Verification System" and "FANS-C Watchdog" are registered.

## 3. First-run configuration

- [ ] `.env` created from `.env.example` (via `setup.ps1` or manually);
      `SECRET_KEY` and `EMBEDDING_ENCRYPTION_KEY` set to real generated
      values, not placeholders.
- [ ] **v2.2.0-specific**: read the updated "Secure-cookie mode" section in
      `.env.example` — `SECURE_COOKIES` should be left **unset** in almost
      every deployment now; the new
      `fans.middleware.DynamicCookieSecurityMiddleware` handles the
      HTTP-fallback case automatically and per-request. Only set
      `SECURE_COOKIES` explicitly if this deployment has an unusual
      requirement the middleware doesn't cover.
- [ ] **v2.2.0-specific (optional)**: review the new "Fraud Detection
      Thresholds" section in `.env.example` — all ten `FRAUD_*` variables
      are commented out with safe defaults; only uncomment/tune them if
      this site's staff headcount or stipend-day volume is producing too
      many or too few Security Review flags. Not required for first launch.
- [ ] `ALLOWED_HOSTS`, `CSRF_TRUSTED_ORIGINS`, `SECURE_PROXY_SSL_HEADER`,
      TLS certificate setup — follow `docs/DEPLOYMENT-CHECKLIST.md` in
      full (unchanged by v2.2.0).
- [ ] First launch reaches the **Create Admin** screen; create the real
      site administrator account (not a dev/test credential).

## 4. v2.2.0 feature verification (fresh install)

- [ ] Log in; confirm the admin menu shows the reorganized 5-category
      structure (User Management / Verification / Distribution /
      Monitoring / System) and every expected page loads.
- [ ] Bell icon shows 0 unread with no badge on a brand-new install (no
      notifications exist yet).
- [ ] Create a test stipend event dated in the future, leave it
      unapproved — confirm the dashboard does **not** label it "Next
      Payout," and a separate "awaiting approval" notice appears instead.
- [ ] Approve it on time (before its date) — succeeds without requiring a
      reason; dashboard now shows it as "Approved."
- [ ] Analytics → Executive tab loads; the two new charts (Beneficiary
      Growth, Monthly Distribution) render (will be empty/flat on a fresh
      install with no history — that is correct, not a bug).
- [ ] Security Review page (renamed from "Fraud Signals") loads and shows
      all 5 signal sections, all empty on a fresh install.
- [ ] Log in over the plain-HTTP LAN-IP fallback URL (if this deployment
      supports it) and refresh the page — confirm the session survives the
      refresh (the v2.2.0 regression fix). Then confirm the primary HTTPS
      URL's session cookie still shows the `Secure` flag in DevTools —
      unaffected by the fix.

## 5. Backup verification

- [ ] Run `scripts\admin\daily-backup.ps1` manually once; confirm a
      manifest is produced and `verify-backup.ps1` reports restore-ready.
- [ ] Confirm the scheduled daily backup task is registered and enabled
      (unchanged from v2.1.x — re-verify here since it's easy to miss on a
      fresh install).

## 6. Go-live

- [ ] Full `docs/DEPLOYMENT-CHECKLIST.md` "Browser Access Test" and
      "Post-Deployment Verification" sections completed.
- [ ] Reboot the server once; confirm auto-start and watchdog both come up
      cleanly.
- [ ] Record deployment details in the "Notes for This Deployment" section
      of `docs/DEPLOYMENT-CHECKLIST.md`.
