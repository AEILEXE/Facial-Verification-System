# FANS-C v2.2.0 — Upgrade From Previous Version Checklist

Scope: updating a server that already runs a prior FANS-C version (v2.1.16,
v2.1.17, or v2.1.18) with real production data — beneficiaries, embeddings,
verification history, payout records — in place. Do **not** use the fresh
production-deployment checklist for this; that checklist assumes no
existing data and will not walk through backup/migration steps.

---

## 1. Before touching anything

- [ ] Confirm the currently-installed version (Settings/System page, or
      installed program version in Windows "Apps & Features").
- [ ] **Back up the database**: `Copy-Item db.sqlite3
      "db.sqlite3.backup-$(Get-Date -Format 'yyyyMMdd-HHmm')"` (or a
      PostgreSQL dump if this deployment uses `USE_SQLITE=False`).
- [ ] **Back up `.env`**: `Copy-Item .env
      ".env.backup-$(Get-Date -Format 'yyyyMMdd-HHmm')"` — contains
      `EMBEDDING_ENCRYPTION_KEY`; losing this makes all stored face
      embeddings permanently unreadable.
- [ ] Run `scripts\admin\daily-backup.ps1` once manually as an additional,
      independent full backup immediately before the upgrade, and confirm
      with `verify-backup.ps1` that it is restore-ready.
- [ ] Note the pre-upgrade test/verification counts if available (from the
      System Health or Analytics pages) so a post-upgrade sanity check has
      a baseline to compare against.

## 2. Install

- [ ] Run `FANS-C-Setup-v2.2.0.exe` as Administrator on the existing
      machine.
- [ ] **Upgrade dialog** appears (not the fresh-install dialog) — confirms
      the installer correctly detected the prior version.
- [ ] Installer's process-kill step (`CurStepChanged`) stops any running
      `fans_c.exe` before overwriting files — confirm no "file in use"
      errors during install. If one occurs, stop `fans_c.exe` manually
      (`taskkill /IM fans_c.exe /F`, or `wmic process where
      name='fans_c.exe' delete` if denied) and re-run the installer.
- [ ] Installer completes with no errors.

## 3. Post-install migration and config

- [ ] On first launch after upgrade, confirm Django migrations run
      automatically (or run `manage.py migrate` manually if this
      deployment doesn't auto-migrate on startup) — this release adds 4
      new migrations: `logs/0012_expand_notification_categories_priority`,
      `logs/0013_update_display_labels_v2_2_0`,
      `verification/0021_add_late_approval_reason`,
      `verification/0022_update_display_labels_v2_2_0`. None of these are
      destructive (no column removed, no data transformed) but confirm
      `showmigrations` shows all four applied.
- [ ] Existing `.env` is preserved by the installer (upgrade does not
      overwrite it) — confirm `EMBEDDING_ENCRYPTION_KEY` and
      `SECRET_KEY` are unchanged from before the upgrade.
- [ ] **v2.2.0-specific**: no `.env` changes are *required* for the
      upgrade to function — `DynamicCookieSecurityMiddleware` and the new
      `FRAUD_*` thresholds all have safe built-in defaults. Optionally
      review the refreshed "Secure-cookie mode" comment block in
      `.env.example` against this deployment's existing `.env`; if
      `SECURE_COOKIES=False` was previously set as a workaround for the
      refresh-logout bug, it is now safe to remove that line (the
      middleware supersedes it) — confirm with a test login over the
      plain-HTTP fallback URL before removing it in production, though
      leaving it in place is also harmless.

## 4. Data continuity verification (the part unique to an upgrade)

- [ ] Existing beneficiary records still list correctly and photos still
      display (checks the blank-avatar fix didn't disturb beneficiaries
      that already had a photo).
- [ ] Existing face embeddings still verify correctly for at least one
      known real beneficiary — confirms `EMBEDDING_ENCRYPTION_KEY`
      continuity and that no migration touched embedding data.
- [ ] Existing stipend events created before the upgrade still show
      correctly on the dashboard — an already-approved past event should
      **not** newly disappear or newly show as "pending" because of the
      `approval_status` filter fix (that fix only changes which pending
      events are *hidden* from "Next Payout," not approved ones).
- [ ] Existing notifications (if any) still display correctly in the bell
      dropdown despite the category set expanding from 4 to 7 — old
      notifications keep their original category value; the display-label
      migration (`0013_*`) is label-text-only, not a data migration, so no
      existing row's `category` value changes.
- [ ] Existing audit log entries with "Fallback"-labeled actions still
      display under their new "Manual Verification" wording without any
      broken links or missing data (label-only rename, confirmed
      non-destructive by reading `logs/migrations/0013_*` and
      `verification/migrations/0022_*`).

## 5. Smoke test

- [ ] Run `scripts\admin\verify-installation.ps1` — all PASS.
- [ ] Run `scripts\admin\check-system-health.ps1` — all OK.
- [ ] Log in as an existing (pre-upgrade) admin account — no forced
      password reset, no broken session.
- [ ] Perform one real verification with an existing beneficiary — succeeds
      end-to-end.
- [ ] Reboot the server once; confirm auto-start and watchdog both come up
      cleanly with the upgraded version.

## 6. Rollback readiness

- [ ] Confirm the pre-upgrade `db.sqlite3.backup-*` and `.env.backup-*`
      files from Section 1 are present and their timestamps match this
      upgrade window — see `docs/ROLLBACK-PROCEDURE.md` if a rollback
      becomes necessary.
