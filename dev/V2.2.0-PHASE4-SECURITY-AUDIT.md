# FANS-C v2.2.0 — Phase 4: Security Release Audit

Code-level audit performed by grep/read against the actual codebase (not
assumed from documentation). Scope: confirm no security regression was
introduced by the v2.2.0 changes, and that the existing security posture
holds.

## CSRF

- No `@csrf_exempt` anywhere in the codebase (`grep -rn csrf_exempt` — zero
  matches). All state-changing views rely on Django's default CSRF
  middleware + template `{% csrf_token %}`.
- `CSRF_TRUSTED_ORIGINS` documented and required for the HTTPS/Caddy
  reverse-proxy path (`.env.example`); unchanged by v2.2.0.

## Cookies / sessions

- `SESSION_COOKIE_HTTPONLY = True`, `X_FRAME_OPTIONS = 'DENY'` — unchanged.
- `SESSION_COOKIE_SECURE` / `CSRF_COOKIE_SECURE` driven by `_secure_cookies`
  (True whenever `DEBUG=False` unless explicitly overridden) — unchanged
  base behavior. The v2.2.0 addition, `DynamicCookieSecurityMiddleware`,
  only ever **weakens** the `Secure` flag on a per-request basis, and only
  for a request that already arrived over plain HTTP (i.e., a request for
  which the flag provided no real protection in the first place, since the
  data was already sent unencrypted). It never touches a cookie on a
  request that arrived over HTTPS — verified by
  `fans/tests.py DynamicCookieSecurityMiddlewareTest`, which asserts the
  `Secure` flag survives unchanged on an HTTPS-proxied request.
- Middleware ordering confirmed: `DynamicCookieSecurityMiddleware` is first
  in `MIDDLEWARE`, so its response-phase code (Django's middleware is an
  onion — response phase runs bottom-to-top) executes **last**, after
  `SessionMiddleware`/`CsrfViewMiddleware` have already set their cookies.
  Correct placement was verified by reading Django's middleware execution
  model, not assumed.

## Secrets

- `SECRET_KEY` and `EMBEDDING_ENCRYPTION_KEY` both fail closed: `settings.py`
  refuses to start (raises `ImproperlyConfigured`) if either is empty or
  equals a known placeholder string while `DEBUG=False`.
- `.env.example` contains no real secrets — `SECRET_KEY=` and
  `EMBEDDING_ENCRYPTION_KEY=` are both blank, with instructions to generate
  real values. No hardcoded credentials found anywhere in `fans/settings.py`
  or the v2.2.0-changed files.
- No new secret-bearing setting was introduced this release; the ten new
  `FRAUD_*` threshold env vars are plain integers, not sensitive.

## Debug exposure

- `DEBUG = _bool_env('DEBUG', default=False)` — defaults closed; `.env.example`
  ships `DEBUG=False`.
- No `debug_toolbar` or equivalent import anywhere in the codebase (grep
  confirmed only comment references explaining *why* DEBUG must stay off).
- Custom error handlers (`fans/urls.py`) are registered for use when
  `DEBUG=False`, so a production 404/500 does not leak a traceback.

## Permissions / access control

- Every new v2.2.0 admin-only view (analytics tabs, Security Review page,
  Password Reset Request queue, Notification Center) follows the existing
  codebase convention of an inline `if not request.user.is_admin` check
  inside a `@login_required` view — confirmed by reading each view added
  or modified this release, not assumed from the pattern's prevalence
  elsewhere (84 total `is_admin`/`login_required`/`@require_POST` usages in
  `verification/views.py` alone).
- `PayoutApprovalWorkflowTest` and `AdminMenuReorganizationTest` both
  include explicit non-admin-denied assertions for the new/changed views.
- The Security Review (fraud) page's "view/flag-only, never blocks"
  invariant is protected by a dedicated regression test asserting none of
  the five signal functions or the view ever write to `is_active`,
  `account_status`, or any other model field.

## Audit logging

- All new state changes this release are audit-logged: late-payout
  approval reason (`late_approval: true` in the `AuditLog.details`),
  password-reset-request approval (`source: self_service_request`),
  backup completion/failure, login-lockout security alert.
- No existing `AuditLog` write path was removed or weakened this release.

## No bypasses introduced

- The refresh-logout fix was deliberately implemented as a narrowly-scoped
  middleware that only ever loosens a cookie flag for traffic that was
  already unencrypted — it does not touch `ALLOWED_HOSTS`,
  `CSRF_TRUSTED_ORIGINS`, authentication, or any permission check.
- No new setting defaults to an insecure value; every new v2.2.0 setting
  (fraud thresholds, notification priority) is either a plain business-logic
  value or has a documented safe default.

## Conclusion

No security regression identified. The one behavior change with any
security surface — `DynamicCookieSecurityMiddleware` — is narrowly scoped,
tested for both the HTTP and HTTPS paths, and net-improves availability
(prevents accidental lockout on the supported fallback path) without
weakening the HTTPS path at all.
