# FANS-C v2.2.0 Gap Analysis Report

Audited against the running v2.1.18 codebase (706 tests passing). Evidence-based — every finding below was confirmed by reading the actual code, not assumed from the brief.

## 1. Existing features (already built, do not rebuild)

- Notification model + bell/badge/dropdown + click-to-navigate + `notify_admins()`/`notify_user()` with dedupe (`logs/models.py`, `logs/notifications.py`)
- Analytics: Executive/Operational/Security dashboards, Chart.js (local, no CDN), CSV export (`verification/analytics.py`)
- Fraud detection: `repeated_failures`, `anomalous_staff_volume`, `mass_edit_detection` with LOW/MEDIUM/HIGH risk banding (`verification/fraud_signals.py`)
- Password recovery: self-service request → admin approval workflow (`accounts/models.py PasswordResetRequest`)
- Face verification: quality scoring, multi-template matching, liveness/PAD, duplicate-face detection, appearance-drift advisory signal (never auto-rejects)
- Admin nav partially organized (6 groups: Accounts & Roles, Verification & Claims, Dashboards, Reports, Settings, IT & Network)
- Org chart, tiered hierarchy view

## 2. Missing features (confirmed gaps)

## 3. Bugs discovered

| # | Bug | Evidence | Severity |
|---|---|---|---|
| 1 | **Dashboard shows unapproved payout schedules as "Next Payout"** | `beneficiaries/views.py:61-67` — `upcoming_events`/`next_event` filter only by `is_active=True` and date range, never by `approval_status`. A `pending_approval` event renders identically to an approved one on the main dashboard. Confirmed real. | High — directly matches the reported issue |
| 2 | **Session/CSRF cookies marked `Secure` even for HTTP-only fallback access, can cause apparent logout-on-refresh** | `fans/settings.py:439-472` — `SESSION_COOKIE_SECURE`/`CSRF_COOKIE_SECURE` both tied to one global `_secure_cookies` flag (True by default in production), with no per-request scheme detection. A browser silently drops `Secure`-flagged cookies received over plain HTTP, so a session created while accessing via the HTTP LAN-IP fallback (a supported access mode in this system) won't survive a refresh. An escape hatch exists (`SECURE_COOKIES=False` in `.env`) but it's global and all-or-nothing — can't serve both HTTPS (primary) and HTTP fallback (secondary) correctly at once today. | High — matches the reported issue, root cause identified |
| 3 | **Beneficiary list table shows a blank cell instead of a placeholder when no profile picture exists** | `templates/beneficiaries/list.html:71-74` — `{% if b.profile_picture %}` with no `{% else %}`. The detail page (`detail.html:176-184`) already has the correct icon-placeholder pattern — the list view just never got it. | Low — cosmetic |

## 4. UX problems

- "Fallback" terminology is user-facing in 14 templates (login help, dashboards, audit/verification logs, print reports, `verification/fallback.html` itself) — technical jargon for what is, from a beneficiary/staff perspective, "manual verification via ID check." Renaming is display-text only; internal URL name (`verification:verify_fallback`), model fields, and Python identifiers stay unchanged — renaming those would be an unrequested refactor of working code.
- "Fraud Signals" nav label reads as accusatory for a government system; "Security Review" is softer and was the user's own suggested replacement.
- Beneficiary list avatar gap (bug #3 above) is also a UX issue.

## 5. Security concerns

- Bug #2 above is the only security-adjacent finding — not a vulnerability (Secure-flagged cookies are the *correct* default), but a deployment-mode gap that could push an admin toward disabling `SECURE_COOKIES` globally (weakening the HTTPS path) just to fix the HTTP fallback path. The correct fix is per-request scheme-aware cookie security, not a global toggle.
- No new authentication/authorization vulnerabilities found. Role gating, CSRF trusted origins, and password policies are unchanged from the already-hardened v2.1.x baseline and were not touched.

## 6. Recommended implementation order

Matches the user's stated phase priority, with the two confirmed bugs folded into the phases that own that subsystem rather than treated as a separate cleanup pass:

1. **Phase 1 — Notification system** (highest priority, as directed): expand categories to the 7 requested, add `priority`, wire `PASSWORD_RESET_REQUEST`/`SECURITY_ALERT` into existing creation points.
2. **Phase 2 — Payout workflow**: fix bug #1 (approval-status-aware dashboard labeling), add approval timestamp/by/reason fields, late-approval-reason requirement.
3. **Phase 3 — Session/auth**: fix bug #2 (per-request scheme-aware secure-cookie behavior).
4. **Phase 4 — UX wording**: "Fallback" → "Manual Verification Required" (display only), "Fraud Signals" → "Security Review" (display only), fix bug #3 (list avatar placeholder).
5. **Phase 5 — Admin menu redesign**: regroup into User Management / Verification / Distribution / Monitoring / System.
6. **Phase 6 — Analytics expansion**: add beneficiary-growth and monthly-distribution charts to the existing dashboards.
7. **Phase 7 — Fraud intelligence**: move to a 0-100 point risk score, add the 3 missing signal types.
8. **Phase 8 — Password recovery**: already Option B (internal approval) — audit-confirm only, no rebuild needed unless this pass finds a specific gap.
9. **Phase 9 — Face verification intelligence**: already has quality/blur/duplicate/liveness checks and an advisory-only appearance-drift signal (no age-estimation model, by design) — document current state, confirm no gap needs new code.
10. **Phase 10 — Final validation**: full test run, migration check, `manage.py check --deploy`, and the v2.2.0 validation checklist.

Proceeding to Phase 1 now.
